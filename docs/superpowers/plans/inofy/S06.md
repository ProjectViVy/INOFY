# S06 — Wait, Resume and Crash Classification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Authorized multi-wait suspension resumes from a committed compatible checkpoint; crash/ambiguous effects cannot silently replay.

**Architecture:** Per-run Eino CheckPointStore stages bytes; a quiescence barrier closes the effect gate and a single host commit makes waiting/checkpoint/outstanding prompts visible. Resume validates all identities and claims the next generation under a host writer epoch.

**Tech Stack:** Go, pinned Eino stateful interrupt/resume/checkpoint APIs.

**Spec:** [architecture](../../specs/2026-09-28-inofy-architecture.md) §§8.1–8.6; [index](index.md).

## Global Constraints

- `WithCheckPointStore` is not a per-node durable snapshot; only atomic host waiting commit may expose checkpoint.
- All outstanding human waits must be answered together; internal gate interrupts never appear as human prompts.
- Opaque checkpoint envelope binds RunID, generation, digests, exact Eino identity, serializer, host identity, input, usage/checksum/seq; no cross-version conversion.

## Review Focus

- Two waits plus one still-running sibling must not mark waiting until all effects have settled (Task 1).
- Checkpoint stage then failed commit leaves run running/reconciliation-required, never waiting (Task 1).
- Duplicate authorized answer is idempotent; conflicting/partial/unauthorized answers reject (Task 2).
- Crash after output commit but before waiting cannot re-execute effect from older checkpoint (Task 2).
- Cancellation racing wait records known terminal outcome through bounded persistence context (Task 2).
