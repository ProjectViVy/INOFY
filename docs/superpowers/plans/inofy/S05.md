# S05 — Bounded Execution and Durable Events Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every leaf effect respects limits, trusted authority, stable operation identity and committed start/result evidence.

**Architecture:** The run-scoped wrapper sits between Eino call lambdas and host `NodeExecutor`; `RunStore.Commit` controls progress visibility. A bounded effect semaphore is shared by nested containers; no second dependency scheduler.

**Tech Stack:** Go, Eino compose, context and standard-library synchronization.

**Spec:** [architecture](../../specs/2026-09-28-inofy-architecture.md) §§5.5, 6–8.2; [index](index.md).

## Global Constraints

- Default caps: 64 nodes, 128 edges, 4 parallel leaves, 256 activations, 1/3 attempts, 60-second node/10-minute active run, 1 MiB definition/input/output and 16 MiB retained/checkpoint.
- Host ceilings cannot be expanded by definition; no retry of authorization, unknown outcome or commit failure; same OperationKey across retry/resume.
- No effect before durable start commit; no downstream value before durable result commit. Callbacks alone are not required event evidence.

## Review Focus

- Start commit fault means executor invocation count stays zero (Task 1).
- Sibling success after other sibling failure stays visible; unknown sibling dominates run result (Task 1).
- Response commit fault after effect returns produces recovery_required and no downstream call (Task 1).
- Retry delay honors cancellation and non-replayable effect never auto-retries (Task 2).
- Wait duration does not spend active run time; budgets never reset on resume (Task 2, S06).
